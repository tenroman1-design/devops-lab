# Занятие 12. Кластер приложения в облаке: балансировщик, приватная сеть, отказоустойчивость

Собираем всё вместе. Бэкенд из занятий 8–9 работает на **нескольких ВМ**, перед ними облачный **балансировщик** (тот же reverse proxy, что nginx на занятии 9, только как сервис облака). База — на отдельной ВМ. Серверы **не видны из интернета**: снаружи открыт только балансировщик. Код — модуль `vm` из занятия 11, state — в бакете OBS.

```
                    ┌──────────────── подсеть курса (192.168.8.0/22) ────────────────┐
интернет ──80──▶ ELB ──8000──▶  app-1  ┐                                              │
  (публичный IP)  │   health    app-2  ├──5432/6379──▶  db  (PostgreSQL + Redis)       │
                  │   /health   app-N  ┘                                              │
                  └───────────────────────────────────────────────────────────────────┘
       у app и db нет публичных IP; в интернет (apt, git, образы) они ходят через NAT-шлюз курса
```

| Занятия 8–9 (на ноутбуке) | Занятие 12 (в облаке) |
|---|---|
| `nginx` с `upstream backend_pool` | балансировщик ELB с пулом `lb_pool` |
| `--scale backend=3` | `app_count = 3` |
| `healthcheck` в compose | `lb_monitor` на `/health` |
| сеть `backend-net`, у бэкенда нет `ports` | группы безопасности: 8000 — только для балансировщика, 5432 — только для app |
| пароль в `.env` | пароль в `TF_VAR_db_password` |

## Практика

### Часть 1. Читаем проект (15 мин)

| Файл | Что внутри |

### Часть 2. Заполняем TODO и запускаем (15 мин)

Пять мест: порт бэкенда (в двух файлах), путь health check, IP базы и `for_each` для участников пула. Все ответы — в коде занятий 8, 11 и в соседних файлах.

> Пароль показан в плане как `(sensitive value)` — Terraform прячет переменные с `sensitive = true`. Но в state и в `user_data` ВМ он всё равно есть. Почему так и как сделать лучше — один из вопросов ДЗ.

Пока ВМ загружаются (3–5 минут: установка Docker, `git clone`, сборка образа), откройте консоль cloud.ru:
- **Elastic Cloud Server**: три ВМ, у них **нет** публичных IP;
- **Elastic Load Balance** → ваш балансировщик → **Backend Server Groups**: статус серверов сначала *Unhealthy*, через несколько минут — *Healthy*.

### Часть 3. Проверяем балансировку (15 мин)

```bash
URL=$(terraform output -raw url)
curl $URL                                   # {"service":"backend","served_by":"<prefix>-app-1",…}
curl $URL/health                            # {"status":{"postgres":"ok","redis":"ok"}}
for i in $(seq 10); do curl -s $URL/hits; echo; done
```

`served_by` чередуется (`app-1`, `app-2`), а счётчик `hits` — общий: он живёт в Redis на ВМ `db`. Это та же картина, что на занятии 9, только теперь «контейнеры» — отдельные машины в облаке.

```bash
curl -s -X POST -H 'Content-Type: application/json' -d '{"text":"from the cloud"}' $URL/notes
curl -s $URL/notes                          # written_by — какой сервер записал заметку
```

> 502/503 сразу после `apply` — нормально: серверы ещё собирают образ. Подождите и проверьте статус в консоли ELB.

### Часть 4. Масштабирование: 2 → 3 (10 мин)

В `terraform.tfvars`: `app_count = 3`.

```bash
terraform plan      # + module.app["app-3"] (ВМ) и + sbercloud_lb_member.app["app-3"]. Остальное — без изменений
terraform apply
```

Через 3–5 минут, когда app-3 станет *Healthy*, в цикле `curl` появится `served_by: …-app-3`. Обратите внимание: правило для базы менять не пришлось. app-3 входит в группу безопасности `app`, и доступ к базе у него появился сам (`remote_group_id`).

### Часть 5. Отказ сервера (10 мин)

Пересоздадим один сервер **на работающем сервисе**. Штурман в отдельном окне запускает «мониторинг»:

```bash
while true; do curl -s -m 2 -o /dev/null -w "%{http_code} " $URL/; sleep 1; done
```

Водитель:

```bash
terraform apply -replace='module.app["app-1"].sbercloud_compute_instance.this'
```

Смотрите на консоль ELB и на окно штурмана. app-1 удалён, балансировщик выводит его из ротации, ответы продолжают приходить: `200 200 200…`. Возможна пара ошибок в момент удаления — health check срабатывает не мгновенно. Через несколько минут новая app-1 соберёт образ и вернётся в ротацию.

> Это и есть смысл кластера: отказ одного сервера не равен отказу сервиса.
> Вопрос на подумать: а что будет, если пересоздать `db`?

### Часть 6. Уборка (5 мин)

```bash

```

Проверьте в консоли: нет ВМ с вашим префиксом, нет вашего балансировщика и публичного IP.

## Если что-то не работает

| Симптом | Причина | Решение |
|---|---|---|
| `Invalid reference` / `TODO` при plan | Не все TODO заменены | `grep -n TODO *.tf` |
| `db_password: только латинские буквы…` / `No value for required variable` | Не задан или неверный пароль | `export TF_VAR_db_password="$(openssl rand -hex 12)"` |
| Все серверы в ELB *Unhealthy* дольше 10 минут | Нет правила на 8000 от `100.125.0.0/16` или порт не тот | Проверьте `network.tf` и `lb.tf` |
| Серверы *Unhealthy*, правила верные | ВМ не смогли скачать пакеты или образы: нет выхода в интернет | Спросите преподавателя, включён ли NAT-шлюз курса |
| `curl $URL` → 503 `{"redis":"error…"}` | База ещё запускается или app не видит db | Подождать; проверить правило `db_from_app` |
| `NoSuchBucket` / `AccessDenied` при init | Бакет или ключи | Как в [занятии 11](../lesson11/README.md#если-что-то-не-работает) |
| `Quota exceeded` при apply | Кончились квоты общего проекта | `app_count = 2`, сообщить преподавателю |

Залезть на приватную ВМ и посмотреть лог cloud-init (`/var/log/start-app.log`) можно только через jump-хост. Это задание 1 из ДЗ.

## ⛔ Главное правило: кластер не оставляем

Балансировщик, публичный IP и три ВМ тарифицируются, пока существуют, даже если вы ничего с ними не делаете.

```bash
terraform destroy
terraform state list       # пусто
```
