# Занятие 14. Мониторинг: Prometheus

Мы научились поднимать приложение в облаке, но пока не знаем, что с ним происходит. Работает ли ВМ? Не кончилась ли память? Сколько запросов обрабатывает backend? Сегодня появляется первый инструмент, который отвечает на эти вопросы, — **Prometheus**.

Это первое занятие **модуля «Мониторинг»**. Модуль состоит из трёх занятий, каждое опирается на предыдущее:

| Занятие | Что добавляем | Что видно |
|---|---|---|
| **14** | Prometheus + node-exporter | метрики ВМ, запросы PromQL |
| 15 | Grafana, cAdvisor, blackbox | графики, контейнеры, доступность приложения |
| 16 | Alertmanager, правила алертов | уведомление, когда что-то сломалось |

```
приложение курса (занятия 8–11)
   │
   ├── node-exporter ───────┐   метрики ВМ: CPU, память, диск, сеть
   │                        │
   ▼                        ▼
Prometheus  ◀── pull: раз в 15 секунд сам ходит и забирает метрики
   │
   └── 127.0.0.1:9090 — смотрим через SSH-туннель с ноутбука
```

## Часть 1. Теория (30 мин)

### 1.1. Зачем мониторинг

Три вопроса, на которые должен отвечать мониторинг:

- **Работает ли?** Приложение отвечает на запросы.
- **Насколько нагружено?** Хватает ли CPU, памяти, диска.
- **Что сломалось и когда?** Нужна история, а не только текущее состояние.

Логи отвечают на вопрос «что произошло в конкретный момент». Метрики отвечают на вопрос «как менялось число за время». Для алертов нужны именно метрики: их удобно считать и сравнивать с порогом.

### 1.2. Как устроен Prometheus

- **Pull-модель.** Prometheus сам ходит к сервисам по расписанию и забирает метрики. Сервисы ничего не отправляют. Это называется **scrape**.
- **Цель (target)** — адрес, с которого Prometheus забирает метрики: например, `node-exporter:9100`.
- **Метрика** — число с именем, метками и временем:

```
node_load1{instance="node-exporter:9100", job="node"}  0.42   @ 12:00:15
│          │                                              │       │
имя        метки (labels): по ним фильтруем                значение  время
```

Метки позволяют отличать серии: один и тот же показатель для разных машин или контейнеров.

### 1.3. Типы метрик

| Тип | Что это | Пример | Как читать |
|---|---|---|---|
| **counter** | только растёт (сбрасывается при перезапуске) | `node_network_receive_bytes_total` | через `rate()`: скорость в секунду |
| **gauge** | текущее значение, может расти и падать | `node_memory_MemAvailable_bytes` | как есть |
| **histogram** | распределение, например задержки | позже | через `histogram_quantile()` |

Важное правило: **счётчик сам по себе ничего не говорит**. Число «1 234 567 байт получено» бесполезно. Нужна скорость: сколько байт в секунду — это `rate()`.

### 1.4. Язык запросов PromQL

| Запрос | Что показывает |
|---|---|
| `up` | статус всех целей: `1` — доступна, `0` — нет |
| `node_load1` | средняя загрузка за 1 минуту |
| `rate(node_network_receive_bytes_total{device!="lo"}[5m])` | входящий трафик в байтах в секунду за 5 минут |
| `sum by (job) (up)` | сколько целей в каждой группе доступно |

Фильтр `{device!="lo"}` исключает loopback-интерфейс. `[5m]` — окно, за которое считается скорость.

### 1.5. Node exporter

Prometheus сам по себе не знает, что происходит на ВМ. Метрики машины отдаёт **node-exporter** — небольшая программа, которая читает `/proc` и `/sys` и показывает их в формате Prometheus. Он ставится как ещё один контейнер в ту же сеть.

### 1.6. Хранение

Prometheus хранит метрики на диске ВМ в собственной базе (TSDB). Срок задан флагом `--storage.tsdb.retention.time=7d`: старше 7 дней данные удаляются. Это важно для ВМ с диском 20 ГБ: без срока хранения база будет расти бесконечно.

### Часть 3. Пишем запросы PromQL (25 мин)

В разделе **Graph** (`http://localhost:9090/query`) выполните по очереди запросы и запишите, что означает каждый результат:

1. `up` — сколько целей доступны.
2. `node_load1` — загрузка CPU за минуту.
3. `node_memory_MemAvailable_bytes / 1024 / 1024` — свободная память в мегабайтах.
4. `rate(node_network_receive_bytes_total{device!="lo"}[5m])` — входящий трафик в байтах в секунду.
5. `100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)` — загрузка CPU в процентах.
6. `prometheus_tsdb_head_series` — сколько временных рядов Prometheus держит в памяти.

**Задание:** напишите запрос, который показывает свободную память **в процентах** от общей. Подсказка: `node_memory_MemAvailable_bytes` делим на `node_memory_MemTotal_bytes`.

### Часть 4. Ломаем и чиним (15 мин)

```bash
docker compose stop node-exporter
```

Подождите минуту и откройте **Targets**: job `node` должен стать `DOWN`. Запрос `up{job="node"}` вернёт `0`.

```bash

```

Через минуту цель снова `UP`. Обратите внимание: Prometheus не знает, почему цель недоступна. Он видит только, что ответа нет. Причину ищем в логах: `docker compose logs node-exporter`.

### Часть 5. Граница и уборка (15 мин)

Что Prometheus **не** делает:
- не отправляет уведомлений: это работа Alertmanager (занятие 16);
- не рисует красивых графиков: это работа Grafana (занятие 15);
- не хранит данные вечно: срок задан 7 днями.

Вопрос в зал: почему pull-модель удобнее для мониторинга, чем когда каждый сервис сам отправляет метрики? Ответ: Prometheus сам видит, что цель пропала (`up == 0`), а сервис, который упал, ничего не отправит.

## Итоги занятия

- Prometheus **забирает** метрики по расписанию (pull). Цель — адрес, с которого забирает.
- Метрика — имя, метки и значение. `counter` читаем через `rate()`, `gauge` — как есть.
- `up == 0` — самый простой сигнал: цель недоступна.
- node-exporter даёт метрики ВМ. Порт Prometheus закрыт для интернета и виден через SSH-туннель.
