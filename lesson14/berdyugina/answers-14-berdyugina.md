Занятие 14. Контрольные вопросы

Бердюгина Анастасия

1. Чем Ansible отличается от Terraform?

Terraform создает инфраструктуру, то есть виртуальную машину, сеть, публичный IP, группы безопасности. Ansible работает уже внутри созданной машины, то есть ставит пакеты, кладет конфиги, запускает сервисы

2. Зачем нужен inventory?

Это список серверов, которыми управляет Ansible, и способ подключения к ним: IP, пользователь, SSH-ключ. Без inventory Ansible не знает, куда идти, серверы можно объединять в группы и запускать плейбук сразу на всю группу

3. Что делает become: true?

Выполняет задачи с повышенными правами, как sudo. Для установки пакетов, правки файлов в /etc/nginx и управления сервисами нужны права администратора. У нас подключение выполняется под пользователем root, но become: true оставлено в соответствии с заданием, благодаря этому плейбук будет работать и при входе под обычным пользователем с правами sudo

4. Что такое идемпотентность?

Свойство, при котором повторный запуск не меняет результат, если система уже в нужном состоянии. Ansible описывает желаемое состояние, а не последовательность действий. Это видно на практике: при повторном запуске плейбука получается changed=0

5. Чем command отличается от специализированного Ansible-модуля?

Модуль command просто выполняет команду и сам не понимает, нужно ли что-то менять, поэтому каждый раз считает ее выполненной. Специализированные модули (apt, copy, file, service) сначала смотрят на текущее состояние и меняют его только при необходимости, поэтому они идемпотентны и сообщают ok или changed. Command используют, когда подходящего модуля нет, как в задании для nginx -t, и добавляют changed_when: false

6. Зачем нужен handler?

Это задача, которая выполняется только тогда, когда ее вызвала другая задача через notify. Нужен, чтобы действия вроде перезапуска Nginx происходили только при реальном изменении конфига, а не при каждом запуске плейбука

7. Когда выполняется notify?

Только если задача вернула changed. Если задача вернула ok, handler не вызывается. Сам handler выполняется один раз, даже если его вызвали несколько задач

8. Зачем проверять nginx -t?

Команда проверяет синтаксис конфигурации до перезапуска. Если перезапустить Nginx с ошибкой в конфиге, он может не подняться и сайт перестанет работать. С проверкой плейбук останавливается раньше, а работающий Nginx продолжает жить на старом конфиге. Это было проверено на практике: была убрана точка с запятой после listen 80, nginx -t упал, restart не выполнился, /health по-прежнему отвечал OK

9. Что делает proxy_pass?

Говорит Nginx пересылать запрос на другой адрес, а ответ возвращать клиенту. У нас запросы идут на http://127.0.0.1:8080, где работает Docker-приложение. Клиент видит только Nginx

10. Почему Docker-приложение можно оставить доступным только на 127.0.0.1:80?

Адрес 127.0.0.1 доступен только изнутри самой машины, поэтому снаружи до приложения не достучаться напрямую, только через Nginx. Так безопаснее, а Nginx становится единой точкой входа. По практике: порт 80 на машине уже занят Nginx, поэтому приложение пришлось опубликовать на 127.0.0.1:8080

11. В чём преимущество схемы Internet -> Nginx -> Application перед Internet -> Application?

Приложение скрыто от интернета и защищено. Nginx можно использовать для HTTPS, ограничений, логов, сжатия, кэша, добавления заголовков и отдельных адресов. Можно подключить несколько приложений или балансировать нагрузку, а клиенты при этом ничего не заметят

12. Что произойдёт, если Docker-приложение остановить?

Nginx продолжит работать, но проксировать будет некуда, поэтому на запрос к / он вернет 502 Bad Gateway. Адрес /health при этом все равно ответит OK, потому что отвечает сам Nginx
