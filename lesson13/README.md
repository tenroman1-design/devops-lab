# Занятие 13. Введение в Ansible: настраиваем свою ВМ

Терраформ (занятия 10–12) создаёт ВМ, но не знает, что внутри неё происходит. Сегодня внутрь заходит **Ansible**: он подключается к ВМ по SSH и приводит её к нужному состоянию — ставит пакеты, выполняет команды, пишет файлы, проверяет, что приложение живо. Одним плейбуком — на своей ВМ из занятия 11.

```
terraform apply          ВМ появилась (железо, сеть, ключ)          — Terraform
        │
        ▼
ansible-playbook         ВМ настроена (пакеты, файлы, команды)      — Ansible
        │               по SSH, без агента на ВМ
        ▼
приложение отвечает      curl http://<public_ip>/  →  backend
```

**Длительность:** 30 минут теория, 90 минут практика.

## Часть 1. Теория (30 мин)

### 1.1. Зачем, если уже есть cloud-init

| Инструмент | Когда работает | Что делает |
|---|---|---|
| **Terraform** | создание и удаление ресурсов | ВМ, сеть, диск, ключи |
| **cloud-init** | один раз, при первом старте ВМ | первичная настройка (занятие 11) |
| **Ansible** | в любой момент, сколько угодно раз | настройка и обслуживание уже работающих машин |

cloud-init хорош для «первого запуска», но он работает один раз. Если завтра нужно поменять конфиг на сотне машин, переписывать cloud-init и пересоздавать ВМ — неудобно. Ansible запускают снова и снова, и он меняет только то, что отличается от описания.

### 1.2. Как устроен Ansible

- **Без агента.** На ВМ ничего не ставим, Ansible ходит по SSH и запускает маленькие программы (модули) сам.
- **Декларативный подход.** Описываем *желаемое состояние*: «пакет `jq` установлен», «файл существует с таким содержимым». Не «выполни apt install».
- **Идемпотентность.** Повторный запуск не ломает и не дублирует: если состояние уже такое, задача отмечается `ok`, а не `changed`. Это главное свойство, на котором держится вся идея.

```
ansible-playbook site.yml
  ok:      Установить утилиты          ← уже стоит, ничего не делали
  changed: Записать motd               ← файл поменялся
  ...
  PLAY RECAP: ok=9  changed=1  ...
```

### 1.3. Инвентарь (inventory)

Список машин и групп. Для нас — одна ВМ:

```ini
[web]
203.0.113.10 ansible_user=root ansible_ssh_private_key_file=~/.ssh/id_ed25519
```

Группа `web` — имя, по которому плейбук выбирает хосты (`hosts: web`). Проверка связи — одной командой, без плейбука:

```bash
ansible web -m ping
# web | SUCCESS => { "ping": "pong" }
```

Это **ad-hoc команда**: модуль + хост, без файла. Удобно для проверки, для настройки — плейбук.

### 1.4. Плейбук: плеи, задачи, модули

Плейбук — YAML-файл. Внутри — **play** (для каких хостов), внутри play — **tasks** (список задач). Каждая задача вызывает **модуль**:

```yaml
- name: Настройка ВМ курса        # play
  hosts: web
  become: true                    # sudo
  tasks:
    - name: Установить htop       # task
      ansible.builtin.apt:        # модуль
        name: htop
        state: present
```

Модули именуются полностью: `ansible.builtin.apt`, `ansible.builtin.copy`. Полезные на сегодня:

| Модуль | Что делает |
|---|---|
| `apt` | ставит и обновляет пакеты |
| `copy` | кладёт файл (или текст) на ВМ |
| `file` | создаёт каталог, меняет права |
| `user` | создаёт пользователя |
| `command` | запускает команду **без** оболочки |
| `shell` | запускает команду **через** оболочку (`\|`, `&&`, `>`) |
| `uri` | делает HTTP-запрос и проверяет ответ |
| `debug` | печатает значение переменной |
| `assert` | проверяет условие, падает, если оно ложно |

### 1.5. Переменные, факты, register

Три источника данных, которые вам понадобятся в практике:

- **Переменные** — `vars:` в плее, `{{ app_dir }}` в задачах.
- **Факты** — Ansible сам собирает сведения о ВМ перед началом: `ansible_facts['hostname']`, `processor_vcpus`, `memtotal_mb`. Выключить: `gather_facts: false`.
- **`register`** — сохраняет результат задачи в переменную. Так мы получаем **вывод команд**:

```yaml
- name: Версия ОС
  ansible.builtin.command: lsb_release -ds
  register: os_release          # сюда попадает вся информация о запуске
  changed_when: false

- name: Показать вывод
  ansible.builtin.debug:
    msg: "ОС: {{ os_release.stdout }}"
```

В переменной `register` есть поля: `stdout` (вывод одной строкой), `stdout_lines` (список строк), `stderr`, `rc` (код возврата), `changed`.

### 1.6. command или shell

- `command` — безопаснее и предсказуемее, **не понимает** `|`, `&&`, `>`, переменные окружения оболочки.
- `shell` — понимает всё это, но открывает оболочку. Если конвейер, добавляйте `set -o pipefail` и `args: executable: /bin/bash`.

Важно: и `command`, и `shell` всегда отмечают задачу как `changed`, даже если ничего не поменяли. Поэтому для проверок пишем `changed_when: false`. Иначе идемпотентность не видна.

### 1.7. Чего Ansible не делает

- **Не создаёт ВМ.** Это задача Terraform. Ansible получает уже готовый IP.
- **Не следит за состоянием.** Он запускается по команде. Если нужно «постоянно», это мониторинг (занятие о Prometheus, если будет).
- **Не хранит секреты в открытом виде.** Для паролей — `ansible-vault` или переменные окружения. В нашем курсе пароли не лежат в файлах, как и в занятии 11.

### 1.8. Что сравнить в конце теории

Вопрос в зал: «У нас уже есть cloud-init. Зачем Ansible?» Ответ: cloud-init работает один раз при создании, Ansible работает в любой момент и подтверждает состояние. Для первой минуты жизни ВМ — cloud-init, для обслуживания — Ansible.

## Итоги занятия

- Terraform создаёт ВМ, Ansible её настраивает. cloud-init — только при первом запуске.
- Плейбук = плей + задачи + модули. Задачи описывают состояние, а не действия.
- Идемпотентность: повторный запуск даёт `changed=0`. Для команд и `shell` ставим `changed_when: false`.
- Вывод команд: `command`/`shell` + `register` + `debug`.
- Секреты в плейбуках не храним: переменные окружения или `ansible-vault`.
